# 0.2.2 acceptance record

Date: 2026-11-03. Status: **all CI gates reproduced locally against the pinned host; released as tag `v0.2.2`; live-server qualification pending**.

## Why this release exists

A failed setup confirmation could not be diagnosed from the message it showed. Three defects combined:

1. **Durable errors were rewritten.** A 27-entry allowlist decided which codes survive into the recovery record. The plugin raises 63 codes, so 53 of them — including `invalid_app_password` and `interactive_terminal_required` — were stored as `unexpected_error`. The specific cause was destroyed just when a user needed it.
2. **`awaiting_confirmation` had no next step.** `_result()` returned `next_action: None` for that state, so a failed activation check produced "state · completed steps · error · next:" with an empty end.
3. **Most codes had no guidance.** 51 registered codes fell through to "run doctor --json", which is circular advice for a failure doctor already names.

Two duplication defects were fixed alongside them:

4. **Doctor and the secure-input button disagreed about URLs.** Doctor used its own validator that skipped whitespace and port checks, so it reported `ok` for a page the button could not open (`https://exa mple.com/x`, port 99999, embedded tab). One `parse_page_url` now serves both.
5. **`username` shape was unvalidated in settings.** `config.Account` accepted `me@@x.com`, `a b` and 300-character IDs; only Telegram applied a rule. `config.valid_login` is now the single rule for CLI, Telegram and stored settings, so a value a wizard accepts always loads.

Three decisions were also repeated per surface and could drift apart:

6. **The unfinished-step rule** existed in three copies (service, CLI, Telegram views) as a nested conditional. `onboarding.repair_step()` is now the only definition.
7. **The disable-only marker** was compared against the literal `"not_run_disable_only"` in five places. `onboarding.is_disable_only_preview()` owns it.
8. **The provider list** was spelled out again in the Telegram views. `PROVIDER_ORDER` derives from the validated `config.PROVIDERS` catalog.

## Product changes

- All 63 raised codes are registered as durable recovery evidence; an unknown string is still never persisted.
- `tests/test_error_codes.py` scans raise sites and fails when a new code is not registered, so the drift cannot silently return.
- `awaiting_confirmation` now reports `confirm` or `retry_confirmation`.
- Guidance is grouped for app passwords, terminals, IMAP, saving, storage, delivery, incompatibility, stale setup, busy setup, bad input, missing records and malformed requests — all bilingual.
- Naver/Daum bare login IDs are accepted at the settings boundary, not only in Telegram.
- `repair_step`, `is_disable_only_preview` and `PROVIDER_ORDER` replace per-surface copies of the same decision.
- Release records are published under `docs/releases/`; `docs/superpowers/` stays untracked as local planning history.
