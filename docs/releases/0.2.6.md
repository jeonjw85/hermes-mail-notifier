# 0.2.6 acceptance record

Date: 2026-11-04. Status: **all CI gates reproduced locally against the pinned host; released as tag `v0.2.6`; live-server qualification pending**.

## Why this release exists

0.2.5 made `delivery_failed` specific and told the user to put `TELEGRAM_BOT_TOKEN` in `<HERMES_HOME>/.env`. That advice was wrong for anyone whose token already exists: their setup was fine, and the plugin was the reason the token could not be used.

`send()` runs `hermes send` in a child process built from `_CHILD_ENV`, which excludes credentials. That exclusion is correct for the cron shim and for `check_environment`, where the whole point is to prove a *fresh* process can reload credentials from the profile — forwarding an ambient value would make that gate pass while cron still failed. But `send()` is not that case. It runs immediately, inside the gateway, where the bot token may legitimately exist only in the process environment (`hermes gateway`, a systemd unit, a secret manager). The plugin was starving its own child.

Measured against the pinned host, with the token in the process environment and no `.env`:

| Path | Result |
| --- | --- |
| Child without credentials (0.2.5) | `Platform 'telegram' is not configured ... TELEGRAM_BOT_TOKEN unset` |
| Child with credentials forwarded (0.2.6) | `Telegram send failed: Unauthorized` — the token reached the Bot API |

The second line with a real token is a delivered message. The first line was the reported `delivery_failed`.

## Product changes

- `_SEND_ENV` adds `TELEGRAM_BOT_TOKEN`, `TELEGRAM_HOME_CHANNEL` and `TELEGRAM_PROXY` to the one-shot send environment. These are the destination the user configured; nothing else travels, and the mail password and other profile secrets stay out.
- `_CHILD_ENV` is unchanged, so the cron shim and `check_environment` still prove reloadability and still refuse an ambient-only credential. The two paths are now explicitly different instead of sharing one list by accident.
- `delivery_not_configured` guidance now names the two real possibilities — no credentials anywhere, or an ambient-only token in a process that does not forward it — instead of prescribing `.env` as the only fix.

## Upgrade

1. Restart the Hermes gateway so the updated plugin module is loaded.
2. Run `hermes mail-notifier doctor --live --json`.

`live_delivery` should now pass for a token that exists only in the gateway process. No `.env` edit is needed for that case. If it still reports `delivery_not_configured`, then the process really has no token and `<HERMES_HOME>/.env` is the right place to add one.
