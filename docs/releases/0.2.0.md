## Live-server handoff

The user confirmed Hermes runs on another server and selected completing local checks first. **Actual model accuracy, real IMAP authentication, Telegram receipt and end-to-end latency have not been measured.**

In the configured server profile, after installing the updated checkout:

```sh
hermes mail-notifier doctor --json
hermes mail-notifier doctor --live --json
hermes mail-notifier evaluate --limit 5 --runs 1 --output mail-smoke.json
hermes mail-notifier evaluate --runs 3 --output mail-evaluation.json
```

The full evaluation makes up to 360 model calls. Each run must achieve recall ≥95%, promotion false-alarm rate ≤5%, zero designated critical misses, and no call errors. Review is reported separately and is not a correct confirmed important-mail prediction. The report must identify one consistent model and the same policy/data/settings versions. Smoke runs cannot qualify a release.

For each connected provider, send a new work/personal test email after setup, run `check`, confirm actual Telegram receipt and compare `history show MAIL_ID`. Run `check` again to confirm no duplicate. Record the email arrival, decision and receipt timestamps. These server checks remain open acceptance items.

## Upgrade and recovery

1. Pause the owned cron job (`hermes cron pause JOB_ID`) and wait for any active check to finish. Keep the current profile's settings and database backup before updating the plugin.
2. Install the updated code in the same profile. The first storage open migrates under the run lock and creates `data.db.v1.bak` or `.v2.bak` next to the database. Migration failure rolls back the schema transaction.
3. Run `status --json` and `doctor --json`. Confirm schema 3, account IDs/checkpoints, pending counts and the owned cron job. Resume a deliberately paused job explicitly.
4. Use `queue retry MAIL_ID` or `--account ACCOUNT_ID` to recover pending work. `queue retarget` explicitly changes prepared destinations. Use `reset` only when intentionally abandoning unfinished work and establishing a new mailbox baseline.
5. For rollback, stop all writers before replacing the database. Restore the matching pre-upgrade database together with compatible plugin code; preserve the current database for investigation. Restoring old state can replay mail processed since the backup. Do not open schema 3 with schema-1-only code or discard active WAL sidecars independently of the database.

Retention: normalized bodies until classification or seven days; completed decisions 30 days; up to 200 feedback snapshots for 180 days. Unfinished notifications remain available for recovery. Existing prepared destinations remain fixed even if the Telegram home channel changes.
