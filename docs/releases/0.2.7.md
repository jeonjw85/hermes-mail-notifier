# 0.2.7 acceptance record

Date: 2026-11-04. Status: **all CI gates reproduced locally against the pinned host; released as tag `v0.2.7`; live-server qualification pending**.

## Why this release exists

Two things were confusing about a first install:

1. **The default language was Korean.** A plugin for an open-source host should not presume a locale. Worse, the language was never asked for: it was inferred from `LANG`, so a user with an English shell got English prompts and English summaries whether or not that was what they wanted, and a user with a Korean shell had no way to say otherwise without a flag.
2. **The advanced-settings prompt read "Edit advanced settings? yes/no".** That sounds required. Classification already works without it — the built-in policy is always in the prompt and a custom rule only adds one line on top — but nothing said so, so it looked like a decision you had to make.

## Product changes

- `Settings.language` now defaults to `en`. English is the open-source default; existing saved settings are untouched.
- `setup` asks `Language / 언어 (ko/en) [en]:` once, at the very start of a first install, and applies the answer to both the summary language and the UI language. Blank keeps English.
- The question is asked only when nothing has been chosen yet: it is skipped when `--ui-language` was passed, on `accounts add/edit`, and on any run that already saved a language. A cancelled install stores nothing, so it asks again — the safe behaviour.
- The prompt now says what it is: `Adjust classification criteria? Optional — defaults already apply (senders, keywords, extra rules) [no]:`, and it defaults to no.

Two function defaults also moved to English: `next_action()` and `render_notification()`. Their callers already pass an explicit language, but a caller that omits it was silently getting Korean, which contradicted the new install default.

## Test fixture changes

The suite had over a hundred Korean assertions leaning on the old default. Rather than weaken them, each fixture that checks Korean text now opts in explicitly (`language="ko"`): the service fixture, the crash-recovery worker, the load scenario, and the diagnostics fixture. Tests that assert English continue to use the default. `test_new_user_must_confirm_and_defaults_come_from_locale` became `test_new_user_chooses_language_and_then_confirms`, and a new `test_korean_choice_is_honoured_even_when_the_locale_is_english` covers the case the locale-inference design used to make impossible.

Three new setup tests: the language question applies to both fields, English and blank both keep `en`, and an existing installation is never asked again. Two more pin the English function defaults and the bilingual `next_action` calls.

`plugin.yaml`'s `language` default moved to `en` as well, so the schema a fresh install reads agrees with the code.

## Upgrade

1. Restart the Hermes gateway.
2. Existing installs keep their saved language. Nothing changes unless you want it to.

To switch an existing install:

```
hermes mail-notifier setup --ui-language ko
```

Or set `language` in the plugin's `configuration` snapshot. The summary language controls the mail text; the UI language controls prompts and guidance.
