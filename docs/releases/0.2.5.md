# 0.2.5 acceptance record

Date: 2026-11-04. Status: **all CI gates reproduced locally against the pinned host; released as tag `v0.2.5`; live-server qualification pending**.

## Why this release exists

Doctor reported `live_model: ok` and `live_delivery: error / delivery_failed`, with advice to check the bot connection and the `telegram:chat_id[:thread_id]` destination. Both were already correct.

`send()` had the same defect 0.2.3 fixed for model calls: one catch-all. Every failure — no adapter, a rejected token, a blocked bot, a wrong chat id, a 429, a timeout, or an entirely unconfigured platform — became `delivery_failed`. The host had already written a precise explanation and the plugin threw it away.

The specific case behind the report is worth stating, because it is not obvious and no amount of "check Telegram" would find it:

`send()` runs `hermes send` in a fresh process with a minimal environment, deliberately excluding credentials. `check_environment` uses that same list to prove a fresh process can *reload* the credentials from the profile — forwarding an ambient token would make that gate pass while cron still failed, so the strip is correct. The consequence is that a `TELEGRAM_BOT_TOKEN` living only in the gateway process is invisible to this child. The host reports it exactly:

```
Platform 'telegram' is not configured. Looked in: <HERMES_HOME>/.env (missing),
<HERMES_HOME>/config.yaml (no platforms.telegram block), environment (TELEGRAM_BOT_TOKEN unset),
external secret sources (none configured). A gateway (pid N) running from <HERMES_HOME> has
telegram connected, so its credentials live only in that process's environment; add
TELEGRAM_BOT_TOKEN/TELEGRAM_HOME_CHANNEL to <HERMES_HOME>/.env.
```

Verified against the pinned host both ways: with the token only in the process environment the child reports `delivery_not_configured`; with the same token in `<HERMES_HOME>/.env` the child reloads it and reaches the Bot API (`delivery_auth_failed` for a fake token). Forwarding the token instead of reading from `.env` was rejected — it would defeat the reload gate.

## Product changes

- Delivery failures carry a specific code:
  - `delivery_not_configured` — the profile has no Telegram credentials the child can see
  - `delivery_no_adapter` — the gateway is not running with that platform connected
  - `delivery_auth_failed` — the bot token was rejected
  - `delivery_forbidden` — blocked by the user, not a member, or missing rights
  - `delivery_destination_not_found` — the chat, user or thread does not exist
  - `delivery_rate_limited` — 429 or flood control
  - `delivery_timeout` — no answer within the timeout
  - `delivery_failed` / `delivery_unverified` — genuinely unclassified, or no message id
- Each has bilingual guidance naming the fix, including the `.env` remedy for the credential-scope case.
- Classification reads only the host's error text to choose a code; it never persists or displays provider text, and no token is ever echoed.
- A subprocess timeout is now distinguished from other spawn failures instead of collapsing into the generic code.

## Upgrade

1. Restart the Hermes gateway so the updated plugin module is loaded.
2. Run `hermes mail-notifier doctor --live --json` and read the new delivery code.
3. If it is `delivery_not_configured`, add `TELEGRAM_BOT_TOKEN` and `TELEGRAM_HOME_CHANNEL` to `<HERMES_HOME>/.env`. A token that exists only in the gateway process cannot reach the plugin's fresh process.
